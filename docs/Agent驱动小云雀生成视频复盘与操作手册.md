# Agent 驱动小云雀生成视频 · 复盘与操作手册

> 复盘范围：2026-08-22 至 2026-11-01，一日一幕系列（`huangzuomin/one-scene-a-day`）45 部成片。
> 读者：需要调用小云雀（剪映云）API、导演制作完整短片的其他 Agent。
> 本文写操作层面的经验（怎么调 API、怎么防事故、怎么审片、怎么发布）。创作规则（节奏/镜头/分镜）见同项目 `PLAYBOOK.md`。

---

## 一、系统概览

| 层 | 组成 |
|---|---|
| 生成端 | 小云雀全能创作 Agent（网页/ API），后端模型 `seedance2.0_fast_vision`（720p/15s 基线） |
| Agent 端 | Linux VM 上的流水线：选题 → 研究 → 概念 → 脚本 → 分镜 → Prompt → 提交 → 下载 → Critic → 发布 |
| 发布端 | GitHub 公开仓库 + GitHub Pages（`huangzuomin/one-scene-a-day`） |
| 定时 | 每日 21:00 流水线；周日 10:00 Learning 复盘 |

**关键事实**：Agent 不直接调视频模型，而是向小云雀的对话式 Agent 提交一段文字简报，由对方生成视频。这意味着——
- 提交是一次**对话消息**，不是结构化 API 调用；
- 生成结果是**概率性的**，同一简报多次提交会产出不同版本；
- 没有幂等键，重复提交会重复扣费（见第三节）。

## 二、小云雀 API 调用

### 2.1 接口清单

| 操作 | 路径 | 说明 |
|---|---|---|
| 提交 | `POST /api/biz/v1/skill/submit_run` | body `{"message": "..."}`，返回 `thread_id` + `run_id` |
| 查状态 | `POST /api/biz/v1/skill/get_thread` | body `{"thread_id": ..., "run_id": ...}`，`thread_id` 与 `run_id` 都必传 |
| 取件 | `POST /api/biz/v1/skill/upload_file` / 视频直链 | 取件 URL 从 `get_thread` 返回的 `biz/x_data_video` 字段取 |

### 2.2 鉴权

- Bearer Token（Access Key）从工作区文件读取：`state/xyq_access_key.txt`（0600）。
- **不要用进程环境变量**——定时任务继承的环境变量可能已过期（2026-08-22 实测教训）。
- 业务错误码 `5` = 正常业务错误（不是鉴权失败）；错误码 `2` = Ak 已过期，需用户更新密钥文件。

### 2.3 传输层：必须用 curl，禁用 urllib

- Python `urllib` 在本机代理环境下发 POST 不稳定：2026-10-12 两次提交报 `RemoteDisconnected`，服务器实际已建单（见 3.1）。
- 提交一律走 `curl`（`tools/xyq/submit_once.py` 已封装）。
- 状态查询可用 `curl` 或 `urllib`（GET 类轻量请求相对稳定），但提交必须用 curl。

### 2.4 状态机

`submit_run` 返回后，`run` 的状态流转：
- `state=1` 提交中 → `state=2` 生成中 → `state=3` 完成（或失败态）
- 轮询间隔 45 秒（不是 10 秒——小云雀生成 15 秒片约需 5–6 分钟，短间隔轮询无意义且浪费请求）。
- 问卷挂起：偶发弹出「创作确认问卷」等待人工输入，`state` 长时间停在生成态。处置：**停手、不重提、等人工在 web 端应答**（T035 挂起 88 分钟、T010 挂起 13 天未解的教训；重提不会加速，只会多扣费）。

## 三、提交幂等性——最重要的教训

### 3.1 四重提交事故（2026-10-12 23:40）

当晚实际产生 **4 个任务实例**，3 次成功扣费，共 270 分（不是台账最初记录的 180 分）：

| 时间 | 方式 | 结果 |
|---|---|---|
| 23:40:29 | Python urllib 提交 | 报 `RemoteDisconnected`，服务器实际已建单（完整版，90 分） |
| 23:40:45 | Python urllib 重试 | 同样报断连，服务器实际已建单（完整版，90 分） |
| 23:40:56 | curl 截断诊断提交 | 未生成视频（测试用） |
| 23:41:18 | curl 正式提交 | 生成成功（发布的正片，90 分） |

**根因**：把「客户端没有收到响应」误判成「服务器没有建单」，随后盲目重试。
**本质**：「未知结果」≠「失败」。`RemoteDisconnected` 的意思是响应丢了，不是请求失败了。

### 3.2 防复发机制（PIPELINE v1.8）

`tools/xyq/submit_once.py`——提交的唯一入口，禁止直接调 `submit_run.py`：

1. **幂等检查**：同一项目已有成功 receipt（`submission_receipt.json`）时拒绝重交（除非 `--force`）。
2. **Ahead-log**：提交前先写 `submit_attempts.jsonl`（时间、消息哈希、状态=attempted），网络调用只发一次。
3. **只走 curl**：单次发送，不自动重试。
4. **未知结果即停手**：断连/超时无响应时 exit 2，**绝不自动重试**。必须先到小云雀控制台（`xiaoyunque.com/history`）核查确认无建单后，才能人工重试。
5. **失败只计「明确失败」**：只有 API 返回 `ret != 0` 才计入「连续失败」；「未知结果」不计入、不触发熔断。

### 3.3 给后来者的铁律

- **永远不要在结果未知时重试提交**。先查控制台，再决定。
- **诊断性提交也是提交**：用真实提交做通路测试会产生真实任务（23:40:56 的截断提交就是一例）。通路测试用只读探测（如查余额、查状态），不要发消息。
- **台账要按实际扣费记**：事后核对控制台的任务数，不要只信客户端日志。

## 四、内容生产流程

### 4.1 选题：七日标签窗（硬规则）

- 每次选题必须**实测**七日窗口（往前推 7 天），不得靠预告或历史缓存判断。
- 同一标签 7 天内不得重复；热门标签有锁定期（如战争标签锁至 10-19）。
- 选题时记录：标签、推荐度、潜力值、质量夜触发条件。

### 4.2 研究：事实与置信分级

- `research.md` 必须标注事实置信级：**A 史料确认 / B 合理推断 / C 艺术创作**。
- 事实清单与视觉元素分开写；L-009 回避清单（时代错误元素）单独列。
- **格式契约**：网站生成器 `gen_site.py` 的 `parse_facts` 只认两种格式——旧式 `| F1 | 事实 | 置信 | 依据 |` 表格，或新式 `- **标签**：内容……A/B/C` 条目。2026-09-10 research.md 换写法后生成器没跟上，导致 8 夜的「研究事实」栏全空（2026-10-13 修复）。**改 research.md 格式时必须同步改解析器**。

### 4.3 创意概念与分镜

- 模板选择：能量决定模板（见 PLAYBOOK R-104a）。
  - **A · 静观四拍**（默认）：安静观察/情绪领悟，3~4.5s 拍。
  - **B · 动作五拍**：动作/救援，1.5~3s 拍×5，hook 即动作。
  - **C · 时间流长镜**：蒙太奇/时间跨度，单镜内时间压缩，禁止多镜快切。
- 每个 Beat 只承载一个信息、一个运动目标（R-107 / R-304）。
- **高风险动作**（跌倒、快转身、起身）必须「起止姿态双重定义」：写清开始和结束时身体的朝向与姿态（见 5.2 的教训）。
- 主角身份锁：开场即固定年龄段、服装、发型、体型，全片重复引用同一描述，禁止中途变化（R-303 / Rule-503）。

### 4.4 Prompt 简报

- 结构：分镜描述（按 R-201 八字段）+ R-401 adherence 约束段 + v1.6 预防句（免确认+整段生成+15 秒硬约束）。
- 预防句是**固定附件**，任何简报模板改动不得删除（Rule-506）。
- 关键器物用「指名+否定式特征注记」（Rule-507）：不要只说「要什么」，还要说「不是什么」（如「后置双推，不是前置单拉」）。

## 五、Critic 评审——最容易漏检的环节

### 5.1 评审方法

- 抽帧：`ffmpeg -vf fps=1` 每秒一帧，重点看开场（f01）、转折（f07）、高潮（f09/f11）、终帧（f15）。
- 评分维度：视觉质量、人物一致性、时代准确性、镜头稳定性、故事清晰度、情感冲击、创意、发布潜力。
- 评分 8.5+ 且无硬伤 → 建议精选。

### 5.2 抽帧评审会漏检动态问题（2026-10-13 教训）

马拉松 T045 首版（23:41:18）抽帧评审 8.8 建议精选，但用户指出倒地镜头有幻觉。后续三版对比发现两类动态缺陷，**静态抽帧都看不出来**：

| 缺陷类型 | 表现 | 哪一版 |
|---|---|---|
| 倒地幻觉 | 倒地动作本身变形 | 首版（23:41:18） |
| 朝向连续性断裂 | 向前扑倒（俯冲），落地却变成仰面躺倒——身体在触地瞬间翻了 180°，物理上接不上 | 第二版（23:40:45） |

**对策**：
- 动作类镜头（尤其跌倒、转身）必须**加密抽帧**（4fps），逐帧看身体朝向的连续性。
- 终帧景别漂移也要查（T040/T013：分镜要求「侧影全身剪影收束」，成片被译为近景/特写 hold）。
- Critic 不能只看首尾帧，**关键动作段必须连续看片**。

### 5.3 版本对比是常态

- 同一简报多次提交会产出不同版本，质量参差。
- 不要默认第一次成功的就是最好的。**有多个版本时，逐版比对关键动作段再定**。
- T045 的最终采用版（23:40:29）是「向后瘫倒」——从头到尾朝向一致，没有翻转。虽然高喊不是正脸特写（与分镜有出入），但连续性自洽，是三版中唯一无硬伤的。

### 5.4 评审纪律

- AI 评分会「失辨别力」（分数挤在窄高段）。人工评级是最终裁决，AI 分只作参考。
- 人工评级积压时，凡涉人工维度的结论一律标注「以 AI 分代读，待评级后复核」，不冒充已验证。
- 评分与发布是两回事：Critic 建议精选 ≠ 用户已评级；待复核队列要单独维护。

## 六、发布链路

### 6.1 生成网站与发布包

- `gen_site.py`：读全部项目，生成 `site/index.html`（含研究事实、分镜、审片信息）。
- `gen_publish.py`：生成 `publish/channels/<日期>/`（README + 封面 + post.txt + 视频）。
- 两个脚本跑完后推送到 GitHub（Git Data API，见 6.2）。

### 6.2 GitHub 发布（无 git clone 的环境）

- 本地不是标准 git clone，用 GitHub Git Data API 推送（`tools/gitpush_api.py`）。
- **关键细节**：更新分支引用必须用 `/git/refs/heads/main`（复数 `refs`），不是 `/git/ref/heads/main`。
- 推送流程：取 base commit → 建 blobs → 建 tree → 建 commit → PATCH ref。
- 大文件（视频 6–12MB）上传慢，超时设 280 秒以上；base64 编码后体积膨胀约 33%。

### 6.3 GitHub Pages 部署延迟

- 推送完成 ≠ 网站立即更新。Pages 部署通常延迟 **1–2 分钟**。
- 两次用户误以为「没发到网站」，实际都是部署延迟。**推送后等 2 分钟再验，不要立即报故障**。
- 验证方法：`curl` 拉取线上页面，`grep` 当夜标题/视频路径确认。

### 6.4 审片页

- `review/index.html`：待人工复核队列（T021/T047/T036/T045 等）。
- 每部片的状态变更（换片、重评）要同步更新审片页备注。
