## 1. 背景与问题

**项目**：「AI 每日短片实验室」——每晚 21:00，一个 AI 会话按 `PIPELINE.md` 自动完成选题→研究→分镜→生成→自评→发布，产出一部 15 秒历史短片。选题池（Topic Pool）决定"每晚拍什么"。

**已上线的治理模型（2026-08-26，PIPELINE v1.3）**：**人管池子，AI 管挑拣**。
- AI 负责提名新选题（周日批量）与每晚挑选（只从 approved 里挑）
- 人负责审批：只有 approved 状态的选题可以开拍
- 数据源是单文件 `topics\topics.json`（无数据库）

**当前痛点（即本次开发动机）**：

| # | 痛点 | 现状 |
|---|---|---|
| P1 | 审核无界面 | 只能靠对话批审（用户对 ZCode 会话说"T006 过"），不可视化、不能随时随地审、批量操作繁琐 |
| P2 | 治理规则无程序化保障 | 库存红线、7 天标签冷却、事件查重、超期冷藏等规则写在 PIPELINE 文字里，靠 AI 会话自觉执行，无校验工具 |
| P3 | 周日补给/体检全靠 AI 手工 | 近重复检测、覆盖矩阵分析没有工具支撑 |
| P4 | 站点看板只读 | 公网站点的选题池板块只能看不能批（静态站，保持只读，不在本次范围） |

## 2. 现状与边界（已存在，勿重复开发 / 勿破坏）

1. **`topics\topics.json`**——选题池唯一事实源，已含 30 条数据（used 5 / blocked 1 / candidate 23）。schema 见 §6。
2. **`gen_site.py`**——静态站点生成器，只读渲染选题池板块（库存预警/可拍队列/待审区/标签战绩）。**勿改**（验收场景 8 会用它做回归验证）。
3. **`PIPELINE.md` §6「选题池治理」**——治理规则的语义权威。你开发的是规则的执行工具，不是规则本身。
4. **并发警告**：每晚 21:00 的自动会话也会写 `topics.json`（把选中条目置为 used）。控制台必须容忍这种并发（见 NFR-05）。
5. 已有的人机交互（对话批审、每晚"明晚预告"、周日 Learning 补给）继续存在——控制台是给用户的**补充界面**，不替代流水线行为。

## 3. 术语

- **状态机**：`candidate（待审）→ approved（可拍）→ used（已拍）`；旁路 `rejected（否决，事件永不复提）`、`blocked（冻结）`
- **四关**（提名质量门）：可考证 / 可拍 / 不撞车 / 有钩子（详见 PIPELINE §5.5）
- **7 天标签窗**：与最近 7 天内 used 的选题主标签相同 → 该选题今夜不可被挑选（冷却中）
- **库存红线**：approved=0 → 红色（当晚停拍）；approved<3 → 黄色预警；≥3 → 绿色
- **推荐分级**：candidate 上的 `recommend` 字段（高/中/低），是主创 AI 给审核人的参考意见

## 4. 功能需求

### P0 · 审核控制台（核心交付：本地 Web UI）

**FR-01 启动**：`python topics_console.py serve` 启动本地服务，浏览器打开 `http://127.0.0.1:8787`。端口可 `--port` 覆盖。

**FR-02 待审列表**：默认视图。每条 candidate 展示：id、题目、pitch（一句话提名理由，重点突出）、标签、年代、潜力分、推荐分级徽章（高=琥珀描边「优先」/中「备选」/低「存疑」）、提名来源与日期。支持按推荐级/标签筛选，按潜力排序。

**FR-03 批准与否决**：单条与批量（勾选多条一键批准）。**否决必填理由**（写入 `rejected.reason`）。所有状态变更立即写回 `topics.json`。

**FR-04 撤销**：approved→candidate（撤销批准）、rejected/blocked→candidate（捞回）允许；**used 是终态，任何界面不提供回退**。

**FR-05 投喂表单**：新增选题（title/event/year/tag/potential/pitch 必填，recommend 可选默认"中"），写入为 `source="user"` 的 candidate。id 自动顺延当前最大编号（格式 `T0NN`）。

**FR-06 库存状态条**：页面顶部常驻。`可拍 N 夜`，按红线规则显示红/黄/绿三态与提示文案（语义与站点板块一致）。

**FR-07 7 天标签冷却提示**：对每条 approved，根据 used 条目（`used_date` 在 7 天内且 `tag` 相同）显示徽章：「今夜可拍」或「冷却中 → MM-DD」。注意这是**提示不是硬拦截**（最终拦截者是流水线）。

**FR-08 标签战绩与覆盖**：
- 标签战绩：只读扫描 `projects\*\`（`concept.json` 的 `topic.tag` + `evaluation.json` 的 `ai_scores.average` + `status.json` 的 `status`），输出每标签 已拍/均分/精选数
- 覆盖矩阵：见 FR-14

**FR-09 数据安全（硬性）**：
- 写入用**原子写**（临时文件 + rename）
- **写前重读**：每次提交变更前重新加载磁盘文件，若磁盘版本与界面加载版本不一致 → 拒绝写入并提示刷新（防 21:00 并发冲突覆盖）
- 每次成功写入前备份到 `topics.json.bak`（轮转保留 3 份：.bak/.bak2/.bak3）
- 写入前 schema 校验，校验失败拒绝并给出可读错误

**FR-10 仅本地**：服务只绑定 127.0.0.1，无任何鉴权/远程访问设计（单用户本机工具）。

### P1 · 治理 CLI（同一文件的子命令，人与 AI 会话共用）

**FR-11 `check`**：全量体检——schema 合法性 / status 枚举 / id 唯一 / used 条目引用的 project 文件夹存在 / 日期格式。输出问题清单，exit code 非 0 表示有错。

**FR-12 `dedup`**：近重复事件检测。比对 candidate 与 used+rejected+blocked+其他 candidate 的 `event`+`title`。实现不求精确：中文分词或字符 bigram 重叠度阈值即可，**宁多报不漏报**，输出疑似对列表供人判断。

**FR-13 `stale`**：`proposed_date` 超 4 周仍是 candidate → 移入 `blocked`（`reason="stale"`）。默认 `--dry-run`，加 `--apply` 才真写。

**FR-14 `stats`**：输出覆盖矩阵（markdown 表）——行=主标签（战争/政治转折/探索发现/日常/科技/艺术/灾难/文明交汇），列=时代分段。时代分段启发式（year 字段是自由文本）：
- 含"前" → 先秦秦汉；朝代名直接映射（汉/唐/宋/元/明/清等）
- 纯数字按公元分段：≤220 秦汉 / ≤589 魏晋 / ≤907 隋唐 / ≤1279 宋 / ≤1368 元 / ≤1644 明 / ≤1912 清 / >1912 近现代
- 无法解析 → "未分类"（宁缺毋滥，不猜）

**FR-15 非交互模式**：`approve T006 T014`、`reject T013 --reason "..."`、`add --title ... --event ...`、`block T004 --reason "..."`。**这是给 ZCode 会话调用的程序接口**——今后对话批审可能改为调 CLI，输出必须机器可读（每命令一行结果，exit code 表达成败）。

**FR-16 `next`（dry-run 挑选模拟）**：按 PIPELINE Step 1 规则（approved 中潜力最高 + 过 7 天标签窗）输出"今夜将选中哪条 + 排除原因清单"。用于核对工具与流水线语义一致。

### P2 · 增强（时间富余再做，不阻塞验收）

- FR-17 candidate 编辑（改 pitch/recommend/potential）
- FR-18 审计日志：所有状态变更追加 `state\topics-audit.jsonl`（时间/命令或界面/变更内容）
- FR-19 一键导出周日 Learning 待审清单（markdown，格式同 Learning 报告末尾附录）

## 6. 数据契约

### 6.1 文件：`topics\topics.json`

```json
{
  "schema": "topics/1",
  "updated": "2026-08-26",
  "note": "选题池唯一事实源……（保留原样）",
  "topics": [ /* 条目数组，见下 */ ]
}
```

### 6.2 条目字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| id | string | ✓ | `T0NN`，全局唯一，不可变 |
| title | string | ✓ | 题目（成片标题的依据） |
| event | string | ✓ | 历史事件名（**查重的关键字段**） |
| year | string | ✓ | 自由文本年代（"208" / "前49" / "唐" / "约1503" / "15世纪初"） |
| tag | string | ✓ | 枚举：战争/政治转折/探索发现/日常/科技/艺术/灾难/文明交汇 |
| potential | int | ✓ | 视觉潜力 1–9 |
| risk_note | string | 可选 | 置信风险备注（如"围城A；守夜士兵C"） |
| status | string | ✓ | 枚举：candidate/approved/used/rejected/blocked |
| source | string | ✓ | 枚举：seed/ai_weekly/user |
| proposed_date | string | ✓ | `YYYY-MM-DD` |
| recommend | string | candidate 建议 | 枚举：高/中/低（approved 后可保留字段但不再展示） |
| pitch | string | candidate 建议 | 一句话提名理由（视觉钩子） |
| used_date | string | used 必填 | `YYYY-MM-DD` |
| project | string | used 必填 | 项目文件夹名（`projects\` 下） |
| result | string | used 可选 | 结局摘要（"喜欢 → selected（Critic 8.6）"） |
| reason | string | rejected/blocked 必填 | 否决/冻结理由（blocked 含 stale 标记用 `reason="stale"`） |

**前向兼容**：遇到未知字段一律保留，不得丢弃；`schema` 值变更为 `topics/2` 前须与主创会话确认。

### 6.3 状态转换表（工具允许的转换）

| 从 \ 到 | candidate | approved | used | rejected | blocked |
|---|---|---|---|---|---|
| candidate | — | ✓ 审批 | ✗ | ✓ 审批 | ✓ 审批 |
| approved | ✓ 撤销 | — | ✗ **仅流水线可写** | ✗ | ✗ |
| used | ✗ 终态 | ✗ | — | ✗ | ✗ |
| rejected | ✓ 捞回 | ✗ | ✗ | — | ✗ |
| blocked | ✓ 捞回 | ✗ | ✗ | ✗ | — |

### 6.4 库存红线（UI 复制此语义）

- `approved == 0` → 红色：「池空：今晚按规则跳过，等待人工批准」
- `approved < 3` → 黄色：「弹药不足三条，请尽快审批」
- `>= 3` → 绿色：「可拍 N 夜」

## 7. 验收标准（逐条可执行）

用 `topics.test.json` 副本执行（NFR-06）：

1. **启动**：`python topics_console.py serve` → 浏览器看到 23 条待审，推荐分级徽章正确，库存红条（0 可拍）
2. **批量审批**：勾选 7 条"优先"一键批准 → 数据文件原子更新 → 刷新后库存变绿「可拍 7 夜」
3. **否决**：否决 T013 并填理由 → 出现在"冻结与否决"区且带理由
4. **投喂**：表单新增一条 → id 顺延（T031）、source=user、进入待审区
5. **冷却提示**：批准 T025（灾难）后，因 used 区 T008（灾难，08-26）在 7 天窗内 → T025 显示「冷却中 → 09-02」
6. **CLI 通道**：`python topics_console.py approve T006` 与 `next` 输出符合 FR-15/16（next 应跳过冷却中的灾难标签条目）
7. **体检**：`check` 对故意改坏的副本（非法 status、重复 id）报出全部错误且 exit≠0
8. **主线回归**：对真实 `topics.json` 做一次 approve 后运行 `python gen_site.py`，确认站点正常生成、选题池板块反映新状态；随后把测试变更回滚（用 .bak 或手工），确保真实数据无残留变更

## 8. 验收流程

开发完成后：在仓库根目录运行 `python topics_console.py check`（真实数据应全绿）+ 上述 8 场景自测记录一并交付（README 或 SELFTEST.md）。最终验收由用户与主创会话执行（含一次 21:00 流水线并行运行的无冲突验证，可选）。
